# 数据库响应速度优化方案

> 适用系统：市场研究驾驶舱
> 数据库：本地 SQLite（`server/stock-db.cjs`，基于 Node 内置 `node:sqlite`）
> 目标：在不改变现有业务功能与对外接口的前提下，提升数据库层响应速度与并发能力，兼顾短期性能改善与长期可维护性。

---

## 现状与瓶颈分析

当前数据库层已启用的基础优化：

- `PRAGMA journal_mode = WAL` —— 读写并发不互斥
- `PRAGMA synchronous = NORMAL` —— 牺牲少量崩溃丢失换取写吞吐
- `PRAGMA busy_timeout = 5000` —— 写锁等待而非立即报错
- `PRAGMA temp_store = MEMORY` + `cache_size = -20000` —— 临时结果走内存
- 预编译语句缓存（`stmt` 对象）—— 避免重复 SQL 解析
- 精简列读写（`getStockBoards` / `upsertStockBoards`）—— 减少写放大与 JSON 解析

**剩余瓶颈**（经分析）：

1. `DatabaseSync` 为**同步 API**，任何读写都会阻塞 Node 事件循环（单线程）。监控数据显示单线程事件循环是瓶颈（CPU 利用率仅 3.3%）。
2. `getStock` 使用 `SELECT *` 全字段读取 + 全 JSON `u()` 解析，即使只需行业/概念字段也付出全量开销。
3. 高频 upsert 未开启**事务批量**路径（除 `upsertTrends` 外）。
4. 大盘数据（stocks 表）随按需抓取持续增长，无规模上限与索引冗余。
5. 无只读副本 / 连接隔离，监控类查询与业务查询混跑。

## 方案一：事务化高频写入 + 语句级 `finalize` 资源回收

### 技术实现细节

针对 `upsertStock` / `upsertStockBoards` 这类高频单行 upsert，将多次写入合并到**单个事务**中提交，避免每次 `run()` 触发一次隐式 COMMIT（WAL 下每个独立写事务都要 fsync + 写 WAL 尾部）。

- 暴露批量写入 API：`upsertStocks(records[])`，内部 `BEGIN` → 循环 `stmt.upsertStock.run(...)` → `COMMIT`；异常时 `ROLLBACK`。
- 复用 `upsertTrends` 已验证的事务模式（见 [stock-db.cjs](file:///c:/Users/A/Desktop/%E5%B3%B0%E7%AD%96/%E9%A9%BE%E9%A9%B6%E4%BB%93%E6%94%B9%20-%20%E5%89%AF%E6%9C%AC/server/stock-db.cjs) 的 `upsertTrends`）。
- 对不再使用的预编译语句显式 `finalize()`，释放 sqlite 内部资源，防止长连接下语句句柄泄漏。

```js
// stock-db.cjs 新增
function upsertStocks(records) {
  const now = Date.now();
  db.exec("BEGIN");
  try {
    for (const s of records) {
      if (!s || !s.code) continue;
      stmt.upsertStock.run(
        s.code, s.name ?? null, /* ...同 upsertStock 参数顺序... */
      );
    }
    db.exec("COMMIT");
  } catch (e) {
    db.exec("ROLLBACK");
    throw e;
  }
  return records.length;
}
```

### 预期性能提升指标

- 批量写入（≥50 条）相比逐条 upsert：**写吞吐提升约 3~10 倍**（减少 fsync 次数）。
- 单次批量写入平均耗时：从逐条的 ~1-2ms/条 降至事务内 ~0.1-0.3ms/条。
- 事件循环阻塞窗口：从"每写一次阻塞一次"变为"每批阻塞一次"，减少对报价中心 5s 轮询的抖动影响。

### 实施步骤

1. 在 `stock-db.cjs` 新增 `upsertStocks` 批量函数（复用事务模式）。
2. 在 `index.cjs` 的批量抓取流程（如每日板块/概念刷新）中，将逐条 `upsertStock` 调用改为收集后一次 `upsertStocks`。
3. 对一次性指令（搜索/详情抓取）保持单条 upsert，不强制事务。
4. 用 `stress.cjs` 对 `/api/stock-detail` 压测，确认无回归。

### 潜在风险评估

- **低**：事务期间若进程崩溃，该批数据回滚，不产生脏数据；下游已有"失败回退旧值"机制兜底。
- 批量太大时单事务持锁时间延长，可能在 WAL 下短暂阻塞其它写；建议单批上限 500 条。
- 需保证 `upsertStocks` 的字段顺序与预编译语句严格一致，否则 SQLite 绑定错位（用参数名/注释规避）。

## 方案二：精简列读取 + 字段投影（消除 `SELECT *` 与全 JSON 解析）

### 技术实现细节

当前 `getStock(code)` 用 `SELECT *` 拉取全行，再对 `quote/minute/main_forces/concepts` 等 JSON 字段逐一 `u()` 解析。对于"仅需行业/概念/名称"的接口（如 `/api/stock-boards`），付出了全字段 I/O 与全部 JSON 反序列化成本。

- 建立**按需投影**的预编译语句集，各业务路径只取所需列：
  - `getBoardsLight(code)`: `code, name, industry, area, concepts, boards_ts`
  - `getQuoteLight(code)`: `code, quote, quote_ts`
  - `getMinuteLight(code)`: `code, minute, minute_ts`
- 仅在 `stock-detail` 聚合接口需要全量时，才用 `getStock` 全字段。
- 对 `quote/minute/main_forces` 的 JSON 解析做**惰性化**：读取时保留原始字符串，仅当业务真正使用时才 `JSON.parse`，避免"读出来却不用"的浪费。

```js
// 精简投影：只读行业/概念，不触碰 quote/minute 大数据列
getBoardsLight: db.prepare(
  `SELECT code, name, industry, area, concepts, boards_ts FROM stocks WHERE code = ?`
),
```

### 预期性能提升指标

- 单次精简读取（6 列）相比全行 `SELECT *`（16 列）：**I/O 传输量减少约 60%**，对含分钟线大字段的记录尤其显著。
- 省去不必要 JSON 解析：当记录含大 `minute` 数组时，单次读取 CPU 成本可**降低 50% 以上**。
- 因按主键 `code = ?` 查询本身为 O(1)（次毫秒级），本方案收益主要在减少大字段 I/O 与解析，对"高频轻量读取"场景（板块/概念随榜单渲染）收益最大。

### 实施步骤

1. 在 `stock-db.cjs` 的 `stmt` 中新增 2~3 条投影语句。
2. 新增 `getStockBoards`（已有）、`getStockQuoteLight`、`getStockMinuteLight` 等轻量读取函数。
3. 在 `index.cjs` 的 `/api/stock-boards`、`/api/stock-quote` 等轻量接口改用轻量读取，仅在聚合接口保留全量。
4. 对 JSON 字段解析做惰性化（存储原始串，使用时再 parse）。

### 潜在风险评估

- **低**：SQL 投影是纯读优化，不改变数据语义，无脏数据风险。
- 需仔细核对各接口实际需要的字段，避免"投影不够导致 `undefined`"；建议在精简读取函数注释中标明用途。
- 惰性 JSON 解析需确保所有使用路径都做了防御性判断（`null` 时返回 `null`），防 `undefined` 泄漏到前端。

## 方案三：连接分层与读写隔离（监测/读多写少分流）

### 技术实现细节

单 `DatabaseSync` 句柄同时服务业务读写与 `/api/monitor` 的 `stockCount()`/`trendCount()` 统计。监控查询虽为 O(1) 主键计数，但与其让它们与高频业务写混在同一事件循环同步执行，不如做**读/写职责分层**：

- 打开**第二个只读连接** `dbRead`（`new DatabaseSync(DB_PATH, { readOnly: true })`），专门服务监控统计与图表类只读接口。
- 写连接只承担 upsert；读连接承担 select 统计。WAL 模式下读写天然不互斥，双连接进一步隔离执行路径。
- 对 `stockCount`/`trendCount`/`getTrends`/`allStockCodes` 等纯读操作，全部切到 `dbRead`。
- 为 `market_trend` 表 `date` 主键 + `stocks.code` 主键显式建 INDEX（已有主键即索引，主要用于确认无缺失）。

```js
// 只读连接(监控/统计/图表专用)
const dbRead = new DatabaseSync(DB_PATH, { readOnly: true });
dbRead.exec(`PRAGMA temp_store = MEMORY; PRAGMA cache_size = -20000;`);
// 只读预编译语句
const readStmt = {
  count: dbRead.prepare(`SELECT COUNT(*) AS c FROM stocks`),
  trendCount: dbRead.prepare(`SELECT COUNT(*) AS c FROM market_trend`),
  getTrends: dbRead.prepare(`SELECT ... FROM market_trend ORDER BY date ASC`),
  allCodes: dbRead.prepare(`SELECT code FROM stocks`),
};
```

### 预期性能提升指标

- 监控接口 `/api/monitor` 的 DB 状态查询从"与业务写抢事件循环"变为"独立只读路径"，**P95 响应更稳定**（预计下降 20~40%）。
- 图表/趋势只读接口（`getTrends`）不再受同一时刻 upsert 的同步阻塞影响，**读延迟波动降低**。
- 双连接使读与写在 WAL 下真正并行，**并发吞吐提升约 30%**（读不等待写释放事件循环）。

### 实施步骤

1. 在 `stock-db.cjs` 打开只读连接 `dbRead`。
2. 将 `stockCount`/`trendCount`/`getTrends`/`allStockCodes` 及监控类统计迁移到 `dbRead` 的预编译语句。
3. 确认 `market_trend` 与 `stocks` 主键索引存在（`PRAGMA index_list` 校验）。
4. 用 `stress.cjs` 对 `/api/monitor` 与 `/api/health` 压测，观察 P95 稳定性。

### 潜在风险评估

- **中**：只读连接在**长时间运行**下若库文件被替换/迁移，需重新打开连接；当前部署为单进程常驻，风险可控。
- WAL 模式下只读连接读到的是已提交数据，不会读到未提交事务，语义安全。
- 需注意 `readOnly: true` 若连接打开时库文件不存在会失败——必须在写连接建表后初始化只读连接，或用 `PRAGMA query_only` 在同一连接隔离业务调用顺序。

## 方案四：stocks 表分区归档 + 索引瘦身（长期可维护性）

### 技术实现细节

`stocks` 表随按需抓取持续增长。为确保长期性能与可维护性，将**冷热数据分层**：

- **热数据**（近期访问的活跃个股）保留在主表；**冷数据**（长期未访问、仅存行业/概念）归档到 `stocks_archive` 表。
- 通过 `updated_at` 阈值（如 90 天未更新）将冷记录迁移到归档表，主表维持有界规模。
- 归档表与主表同构，读取时先查主表（命中率高），未命中再查归档表（透明回退）。
- 为归档表建独立索引，减少主表索引膨胀。

```sql
-- 归档表(与主表同构)
CREATE TABLE IF NOT EXISTS stocks_archive (
  code TEXT PRIMARY KEY, name TEXT, industry TEXT, area TEXT,
  concepts TEXT, main_business TEXT, boards_ts INTEGER, profile_ts INTEGER,
  quote TEXT, quote_ts INTEGER, minute TEXT, minute_ts INTEGER,
  main_forces TEXT, main_forces_ts INTEGER, created_at INTEGER, updated_at INTEGER
);
```

### 预期性能提升指标

- 主表行数受控（维持在活跃集规模），**全表扫描类操作与缓存命中率更佳**，`stockCount` 等统计更快。
- 归档后主表索引瘦身，**写入时的索引维护开销降低约 20%**（索引更小，B+ 树层数更少）。
- 长期运行（数月）后，查询延迟不会随数据无界增长而劣化，**延迟保持稳定**。

### 实施步骤

1. 建 `stocks_archive` 表（同构）。
2. 新增 `archiveStale() ` 迁移函数：`INSERT INTO stocks_archive SELECT * FROM stocks WHERE updated_at < ?` 后从主表删除（同一事务）。
3. 在每日批量刷新流程末尾调用 `archiveStale()`。
4. 读取路径加归档回退：主表未命中 → 查归档表。

### 潜在风险评估

- **中**：归档迁移是**破坏性写**，需先在备份/副本上验证迁移 SQL 正确性；迁移失败回滚事务。
- 归档后若用户重新打开某只冷股，需从归档表"激活"回主表（或直接读归档+按需抓取新建），需实现回退读取逻辑。
- 迁移时机需错开交易高峰（建议收盘后/开盘前），避免与盘中写入竞争。

## 方案五（补充）：内存缓存前置 + 读多写少的请求合并

### 技术实现细节

对于**短期高频读、长期低频变**的数据（个股行业/概念、财务指标、主营），在 DB 之上再加**进程内内存缓存**（TTL 分层）：

- 行业/概念：`boards_ts` 已存在，可缓存 key=`boards:${code}`，TTL 与 `boards_ts` 刷新周期一致（日级）。
- 财务指标 / 主营：已走 `cached()`（24h），无需内存层。
- 分时/行情：已走 `cached()`（5s/10s），无需内存层。
- 通过 `cached()` 已有的并发合并（inflight）机制，天然避免同一 key 的并发穿透 DB。

### 预期性能提升指标

- 行业/概念高频读取（榜单渲染反复触发）从"每次查 DB"变为"内存命中"，**平均读取延迟从 ~0.5ms 降至 ~0.01ms**。
- 显著减少 DB 连接上的同步读压力，为写操作让出事件循环时间片。

### 实施步骤

1. 复用现有 `cached()` 工具，为 `stock-boards` 增加进程内缓存层（key 含 code）。
2. 确认缓存失效与 `boards_ts` 刷新联动，避免陈旧。
3. 用 `stress.cjs` 压测 `/api/stock-boards` 观察命中率。

### 潜在风险评估

- **低**：内存缓存为纯读加速，有 TTL 保护，最坏情况是短暂陈旧（至多一个刷新周期）。
- 需控制缓存条目上限（复用 `CACHE_MAX`），防用户输入拼 key 导致无界增长。

## 方案对比与优先级建议

| 方案 | 收益 | 风险 | 投入 | 建议优先级 |
|------|------|------|------|-----------|
| 一、事务化批量写 | 写吞吐 3~10x | 低 | 低 | ⭐ 立即 |
| 二、精简列读取 | I/O -60%、解析 -50% | 低 | 低 | ⭐ 立即 |
| 三、读写连接分层 | P95 稳定、并发 +30% | 中 | 中 | 短期 |
| 四、冷热归档 | 长期稳定、无界增长受控 | 中 | 中高 | 中长期 |
| 五、内存缓存前置 | 高频读 50x 加速 | 低 | 低 | 视需 |

**建议路线**：先落地方案一、二（低风险、见效快），再实施方案三（监控与图表稳定），最后按需推进方案四归档（长期可维护性）与方案五。
